EcoRDF vs Virtuoso / Qlever：設計戦略の比較
三者の核心的な違い
Virtuoso はもともとリレーショナルDBエンジンをRDF向けに転用した設計です。B木インデックスとハッシュジョインが中心で、クエリごとにバッファプールからページを読み込みます。実績のある安定したシステムですが、結合を左深木（left-deep tree）で順番に処理するため、多数のパターンが絡む生物系クエリでは中間結果が爆発しやすいです。
Qlever は列指向ストアで、起動時にインデックス全体をメモリにロードします。ロード後のクエリは非常に速いのですが、1億トリプルで数十GB、10億トリプルで数百GBのRAMが前提になります。データセンター規模のサーバーでは有効ですが、普通の研究サーバーでは動かせないことがあります。
EcoRDF の戦略は「OSに任せる」です。memmap2でインデックスをメモリマップし、どのページをRAMに置くかをOSのページキャッシュに委ねます。クエリが触るページだけがRAMに乗り、残りはディスクのままです。
Virtuoso:  バッファプール管理（自前）  → 設定が複雑、メモリ予測が難しい
Qlever:    全データをRAMにロード      → 速いが大量RAMが必須
EcoRDF:    mmap → OSページキャッシュ  → RAMは「実際に使った分」だけ

Leapfrog Triejoinが速い理由
Virtuosoのハッシュジョインは2パターンずつ順番に結合します：
?protein → type → UP:Protein        (結果: 2000万行)
     ↓ hash join
?protein → taxon → taxonomy:9606    (中間結果: 50万行)
     ↓ hash join
?protein → encodedBy → ?gene        (最終: 1万行)
中間に50万行のハッシュテーブルを作ります。
Leapfrog Triejoinは全パターンのイテレータを同時に動かします：
rust// src/sparql/executor.rs の leapfrog_join
// 全イテレータの現在値の最大値を求め、全員をそこへseek()
// → 全条件を同時に満たす値だけを列挙
共通変数に一致する値だけを辿るため、中間結果の物理化が不要です。生物系クエリ（タンパク質×GO term×疾患のような多対多結合）で特に効きます。

スケーラビリティの現実的な見積もり
ディスクサイズはトリプル数に対してほぼ線形です：
トリプル数SPO+POS+OSPGSPO付き1億約 3.6 GB約 5.2 GB10億約 36 GB約 52 GB100億約 360 GB約 520 GB
辞書（dict.bin）は別途かかりますが、トリプル数より少ない（URIの重複が多い）ため通常は全体の10〜20%程度です。
RAM消費はクエリパターン依存です。例えば ?x rdf:type up:Protein のような1パターンスキャンならPOSインデックスの該当範囲（数MB〜数十MB）だけがページインします。ウォームアップ後はOSキャッシュに乗り高速になります。

クエリ実行がシングルスレッドです。executor.rs の execute_plan は逐次実行です。10億トリプルの広いスキャンが絡むクエリは、Qleverの並列スキャンに比べて遅くなります。

ソート済みインデックスのビルドがメモリ内です。AllBuilders はトリプルをVecに積んでからソートするため、ビルド時のピークRAMがデータサイズに比例します。100億トリプルのビルドには数百GBのRAMが必要になります（クエリ時とは別の問題）。

適切なユースケース
EcoRDFが最も輝くのは、10億トリプル前後のデータを研究サーバー（RAM 32〜128GB）で運用するシナリオです。UniProtやTogoIDのような生命科学RDFデータはこのレンジに収まることが多く、Qleverのように「全データをRAMに」を要求せず、Virtuosoのように「重いプロセス管理」も不要です。クエリが選択的（絞り込みが強い）なSPARQLならLeapfrog Triejoinの恩恵が大きくなります。
